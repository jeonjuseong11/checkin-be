## 1. 제품 개요

### 1.1 배경
오프라인 현장(공장, 물류센터, 건설현장, 행사장, 공유오피스)에서의 출입 통제는 두 가지 현실과 충돌한다.

1. **네트워크가 항상 있다는 가정이 깨진다.** 지하 주차장, 엘리베이터 홀, 자재 창고, 산간 현장은 LTE/Wi-Fi 음영 지역이다. 출입 단말이 서버에 닿지 못하는 순간에도 사람은 계속 드나든다.
2. **통제 결과는 즉시, 그리고 정확히 공유돼야 한다.** 관리자는 "지금 누가 안에 있는지"를 실시간으로 알아야 하고, 비상 상황에서는 1초도 늦으면 안 된다. 동시에 현장 담당자는 익숙한 도구(구글 시트)로 명부를 보고 싶어 한다.

`checkin-be`는 이미 멀티테넌트 클라이언트(`app_clients`, API Key 발급/검증)를 갖추고 있다. 이 PRD는 그 위에 **오프라인 내성(offline-tolerant) 출입 이벤트 파이프라인**을 얹어, 음영 지역에서도 데이터 유실 없이 출입을 기록하고, 멱등성으로 중복을 제거하며, 구글 시트 미러링과 FCM 하이브리드 알림으로 결과를 즉시 전달하는 것을 목표로 한다.

### 1.2 한 문장 정의
> 네트워크가 끊겨도 출입 기록을 잃지 않고, 연결이 복구되면 중복 없이 정확히 한 번만 반영하며, 관리자에게는 실시간 시트와 푸시로 즉시 보여 주는 B2B 출입 통제 백엔드.

### 1.3 가장 좁은 웨지 (Narrowest Wedge)
"출입 단말 SDK + 오프라인 큐 + 멱등 수집 API" 한 묶음. 시트 미러링과 FCM은 그 위에 붙는 가치 레이어다. 음영 지역에서 한 건도 잃지 않는다는 신뢰가 이 제품의 첫 번째이자 가장 방어 가능한 가치다.

## 2. 목표와 비목표

### 2.1 목표 (Goals)
- **G1.** 네트워크 음영 지역에서 발생한 출입 이벤트를 단말에 안전하게 큐잉하고, 연결 복구 시 자동 동기화한다. 정상 운영 가정에서 이벤트 유실률 0%를 목표로 한다.
- **G2.** 동일 이벤트가 재전송되어도 서버 상태는 한 번만 변한다(정확히 한 번 반영, exactly-once effect). Redis 기반 멱등성으로 보장한다.
- **G3.** 확정된 출입 이벤트를 테넌트별 구글 시트에 준실시간(목표 p95 ≤ 5초)으로 미러링한다.
- **G4.** 출입/이상 이벤트를 FCM 푸시로 전달하되, 푸시 미수신 환경을 위한 폴백 채널(인앱 인박스, 선택적 webhook)을 갖춘 하이브리드 알림을 제공한다.
- **G5.** 모든 기능은 기존 멀티테넌시·API Key 보안 모델을 그대로 따른다.

### 2.2 비목표 (Non-Goals) — 이번 범위 밖
- 물리 단말(리더기, NFC/QR 하드웨어) 자체의 펌웨어 개발. 본 PRD는 백엔드와 단말 SDK 계약(contract)까지만 정의한다.
- 얼굴 인식·생체 인증 알고리즘. 인증 결과(통과/거절)는 단말 또는 외부 시스템이 판단하고, 본 시스템은 그 결과를 신뢰성 있게 수집·전파한다.
- 근태/급여 정산 로직. 출입 데이터는 제공하지만 정산은 다운스트림의 몫이다.
- 관리자 웹 프런트엔드 풀 구현(별도 PRD). 본 문서는 백엔드 API와 시트 산출물까지.

## 4. 핵심 유스케이스

1. **정상 출입:** 단말이 인증 통과 → 이벤트 즉시 전송 → 서버 멱등 처리·저장 → 시트 반영 + (조건부) 푸시.
2. **음영 구간 출입:** 네트워크 없음 → 단말 로컬 큐에 적재 → 연결 복구 시 일괄 전송 → 서버가 중복 제거 후 시간순 정렬·반영.
3. **재시도 폭주:** 단말이 응답을 못 받아 같은 이벤트를 N회 재전송 → 서버는 첫 1회만 상태 변경, 나머지는 동일 결과를 빠르게 반환.
4. **이상 이벤트:** 비인가 시도·강제 개방·테일게이팅 의심 → 관리자에게 우선순위 높은 FCM 알림 + 인앱 인박스 동시 기록.
5. **사후 감사:** 관리자가 구글 시트 또는 API로 특정 기간 출입 로그를 조회·내보내기.

## 5. 시스템 아키텍처 개요

```
[출입 단말 SDK]
  ├─ 로컬 영구 큐 (SQLite/파일)  ← 음영 구간 버퍼
  └─ 동기화 워커 (지수 백오프 재시도)
        │  HTTPS (API Key + Idempotency-Key)
        ▼
[NestJS API: checkin-be]
  ├─ AuthGuard (기존 app_clients API Key 검증)
  ├─ Ingest Controller  ── 멱등성 검사 (Redis) ──┐
  │                                              │
  ├─ AccessEvent 도메인 서비스 (PostgreSQL 영속) │
  │        │                                     │
  │        ├─▶ [BullMQ on Redis] 비동기 작업 큐  │
  │        │      ├─ Sheets Mirror Worker ─▶ Google Sheets API
  │        │      └─ Notification Worker  ─▶ FCM + 폴백 채널
  │        └─▶ 출입 상태 집계 (현재 내부 인원)    │
  └────────────────────────────────────────◀─────┘
```

- **동기 경로:** 인증 → 멱등성 판정 → DB 커밋 → 클라이언트에 결과 반환. 빠르고 짧게 유지한다.
- **비동기 경로:** 시트 미러링과 알림은 BullMQ(Redis) 잡으로 분리해, 외부 API 지연이 수집 응답을 막지 않게 한다.

## 6. 기능 요구사항

### 6.1 멀티테넌시 & 인증 (기존 자산 재사용)
- 모든 요청은 `Authorization: Bearer chk_...` API Key로 인증한다. 키는 SHA-256 해시(`app_clients.api_key_hash`)로 대조한다.
- 테넌트(`clientId`)는 이벤트, 멱등성 키, 시트, 알림 토큰의 격리 단위다. 한 테넌트의 데이터는 다른 테넌트에 절대 노출되지 않는다.
- `is_active = false` 테넌트의 요청은 거절한다.

### 6.2 출입 이벤트 수집 (Ingest)
- 단일 및 **배치** 수집을 모두 지원한다(음영 구간 복구 시 한 번에 수십~수백 건이 올라온다).
- 이벤트 필수 필드: `eventId`(단말 생성 UUID), `deviceId`, `gateId`, `subjectId`(출입 주체), `direction`(IN/OUT), `decision`(GRANTED/DENIED), `occurredAt`(단말 로컬 시각, ISO8601 + 오프셋), `clientEventSeq`(단말 내 단조 증가 시퀀스).
- 서버는 `occurredAt` 기준으로 정렬·저장하되, 단말과 서버의 시계 차이를 보정하기 위해 `receivedAt`을 별도 기록한다.

#### 6.3 [필수] 오프라인 큐 처리 (네트워크 음영 지역 대응)
**문제:** 음영 구간에서는 전송이 불가능하지만 출입은 계속된다. 단말 메모리에만 두면 재부팅·앱 종료 시 유실된다.

**단말 측 계약 (SDK 요구사항):**
- 모든 이벤트는 전송 전 **로컬 영구 저장소(SQLite 권장)** 에 먼저 기록한다(write-ahead). 전송 성공 ACK를 받은 뒤에만 큐에서 제거한다.
- 각 이벤트는 단말에서 생성한 불변 `eventId`(UUID v4)와 단조 증가 `clientEventSeq`를 갖는다. 이 둘이 서버 멱등성·정렬의 기준이 된다.
- 동기화 워커는 연결 복구를 감지하면 **시간순(seq 오름차순)** 으로 배치 전송한다. 배치 크기 상한(예: 200건/요청)과 **지수 백오프 + 지터**(예: 1s → 2s → 4s … 최대 5분) 재시도 정책을 따른다.
- 큐 적체 상한과 보존 기간을 둔다(예: 최대 50,000건 또는 30일). 상한 초과 시 가장 오래된 것부터가 아니라 **정책에 따라 경고를 올리고** 운영자가 개입하도록 한다(무음 손실 금지).

**서버 측 요구사항:**
- 배치 수집 엔드포인트는 부분 성공을 지원한다. 응답에 이벤트별 처리 결과(`accepted` / `duplicate` / `rejected` + 사유)를 배열로 반환해, 단말이 어떤 항목을 큐에서 지울지 정확히 판단하게 한다.
- 오래된 `occurredAt`(예: 7일 초과 지연 도착) 이벤트도 거절하지 않고 수용하되 `lateArrival = true`로 표시하고, 시트/알림 정책에서 다르게 다룬다(지연 도착 이벤트로 실시간 알림을 울리지 않는다).

**수용 기준 (AC):**
- 단말 비행기 모드 5분 후 복구 → 그 사이 발생한 모든 이벤트가 서버에 정확히 반영된다.
- 동기화 중 앱 강제 종료 후 재시작 → ACK 받지 못한 이벤트는 재전송되고, 중복은 서버가 제거한다.

#### 6.4 [필수] Redis 기반 멱등성
**문제:** 6.3의 재시도 정책은 본질적으로 "최소 한 번(at-least-once)" 전송을 만든다. 따라서 서버는 중복을 흡수해 **효과적으로 정확히 한 번(exactly-once effect)** 을 만들어야 한다.

**설계:**
- 멱등성 키 = `clientId:eventId` (이벤트 자체의 자연 키). 클라이언트가 `Idempotency-Key` 헤더로 배치 단위 키를 추가로 보낼 수도 있으나, 진실의 원천은 이벤트별 `eventId`다.
- 처리 흐름:
  1. `SET idemp:{clientId}:{eventId} <state> NX EX <TTL>` 로 선점을 시도한다.
  2. `NX` 성공 → 신규 이벤트. DB 트랜잭션으로 저장하고, 성공 후 Redis 값에 최종 결과(예: 저장된 `accessEventId`)를 기록한다.
  3. `NX` 실패 → 이미 처리됨. Redis에 저장된 동일 결과를 **재계산 없이** 반환한다(같은 입력 → 같은 출력).
- **경합 처리:** 동시에 같은 `eventId`가 두 요청으로 들어오면, 선점에 진 요청은 "처리 중" 상태를 보고 짧게 폴링/대기 후 확정 결과를 반환한다(이중 INSERT 금지).
- **DB 레벨 안전망:** `access_events(client_id, event_id)`에 **UNIQUE 제약**을 둔다. Redis가 유실되거나 TTL이 만료되어도 DB가 최종 중복 방어선이 된다. UNIQUE 위반은 "이미 존재" 결과로 매끄럽게 변환한다.
- **TTL 정책:** 멱등성 키 TTL은 단말 큐 최대 보존 기간보다 길게 잡는다(예: 35일). 지연 재전송이 TTL 만료 후 도착해도 DB UNIQUE가 받쳐 준다.

**수용 기준 (AC):**
- 동일 이벤트를 1,000회 동시·연속 재전송 → DB에는 1건, 응답은 모두 동일한 `accessEventId`.
- Redis 플러시 후 동일 이벤트 재전송 → DB UNIQUE로 여전히 중복 없음.

#### 6.5 [필수] 구글 시트 실시간 미러링
**문제:** 운영 담당자는 새 대시보드를 배우기보다 익숙한 구글 시트에서 출입 명부를 보고 싶어 한다.

**설계:**
- 테넌트별로 미러링 대상 스프레드시트를 연결한다(`clientId → spreadsheetId + 시트 탭`). 연결은 서비스 계정(Service Account) 공유 또는 OAuth 중 택1(오픈 퀘스천 §13).
- 확정된 `AccessEvent`는 **BullMQ 잡**으로 미러링 워커에 넘긴다. 동기 응답 경로에서 시트 API를 호출하지 않는다(구글 API 지연·쿼터가 수집을 막지 않도록).
- **쓰기 전략:** `spreadsheets.values.append` 기반 append-only 로그 시트를 기본으로 한다. 행 키로 `eventId`를 포함해 재실행 시 중복 append를 막는다(워커도 멱등해야 한다).
- **배칭 & 레이트 리밋:** 구글 Sheets API 쿼터(분당 쓰기 제한)를 존중하기 위해 짧은 윈도우(예: 1~2초)로 행을 모아 일괄 append 한다. 음영 구간 복구로 수백 건이 몰릴 때 특히 중요하다.
- **정합성:** 미러링은 "준실시간 best-effort"다. 시트가 진실의 원천이 아니라 **PostgreSQL이 원천**이고 시트는 파생 뷰다. 워커 실패 시 재시도하며, 장기 실패는 운영 알림으로 올린다.
- **지연 도착(`lateArrival`) 이벤트**도 시트에는 시간순 위치가 아닌 도착순 append로 기록하되 `occurredAt` 컬럼으로 정렬 가능하게 한다.

**수용 기준 (AC):**
- 정상 이벤트 발생 후 p95 ≤ 5초 내 시트에 행 출현.
- 같은 이벤트가 재처리돼도 시트 행은 1개(eventId 기준 중복 append 차단).
- 300건 배치 복구 시 쿼터 초과 없이 모두 반영.

#### 6.6 [필수] FCM 하이브리드 알림
**문제:** 푸시는 빠르지만 신뢰할 수 없는 채널이다(토큰 만료, 기기 오프라인, 권한 거부). 출입 통제 알림은 놓치면 안 된다.

**"하이브리드"의 정의 — 3계층:**
1. **실시간 푸시 (FCM):** 관리자 앱에 즉시 알림. 데이터 메시지 + 알림 메시지 혼합으로 포그라운드/백그라운드 모두 처리.
2. **인앱 인박스 (영속):** 모든 알림은 발송 여부와 무관하게 서버 DB(`notifications`)에 기록된다. 앱이 켜지면 인박스에서 놓친 알림을 동기화한다. 푸시는 전달 가속기일 뿐, 진실의 원천은 인박스다.
3. **폴백 채널 (선택, 테넌트 설정):** 우선순위 높은 이벤트(비인가/강제개방)에 한해 webhook 또는 이메일로 에스컬레이션. 일정 시간 내 인앱 확인(read)이 없으면 단계적 에스컬레이션.

**설계:**
- 토큰 관리: 기기별 FCM 토큰을 `clientId`·관리자 사용자 단위로 저장. FCM이 반환하는 `UNREGISTERED`/`INVALID` 응답 시 토큰을 즉시 무효화·정리한다.
- 알림 생성도 **멱등**해야 한다. 같은 출입 이벤트가 중복 처리돼도 알림은 1회만 발송한다(알림 멱등 키 = `eventId:notificationType`).
- 알림 정책은 테넌트별 룰로 구성한다: 어떤 `decision`/`direction`/게이트에서 누구에게 어떤 우선순위로 보낼지. 기본값은 "DENIED + 이상 이벤트만 푸시, 정상 출입은 인박스만".
- 지연 도착(`lateArrival`) 이벤트는 실시간 푸시를 울리지 않는다(과거 사건으로 사용자를 깨우지 않음). 인박스에는 남긴다.

**수용 기준 (AC):**
- 비인가 시도 이벤트 → 관리자 기기에 5초 내 푸시 + 인박스 기록 동시 충족.
- 푸시 권한 꺼진 기기 → 인박스에는 100% 기록되고, 앱 재실행 시 동기화됨.
- 동일 이벤트 재처리 → 푸시·인박스 각각 1건만.

## 7. 데이터 모델 (신규 핵심 엔티티)

기존 `app_clients`(테넌트)를 부모로 한다.

- **`access_events`** — 출입 이벤트 원천(PostgreSQL).
  - `id` (uuid, PK, 서버 생성), `client_id` (FK), `event_id` (단말 UUID), `device_id`, `gate_id`, `subject_id`, `direction`, `decision`, `occurred_at`, `received_at`, `client_event_seq`, `late_arrival` (bool), `created_at`.
  - **UNIQUE(`client_id`, `event_id`)** — 멱등성 최종 방어선.
  - 인덱스: (`client_id`, `occurred_at`), (`client_id`, `gate_id`, `occurred_at`).
- **`device_registrations`** — 단말/관리자 기기 및 FCM 토큰.
  - `id`, `client_id`, `device_id`, `fcm_token`, `platform`, `last_seen_at`, `is_valid`.
- **`notifications`** — 인앱 인박스(하이브리드 알림의 진실 원천).
  - `id`, `client_id`, `event_id`(원인 이벤트), `type`, `priority`, `payload`, `delivered_push` (bool), `read_at`, `created_at`.
  - UNIQUE(`client_id`, `event_id`, `type`) — 알림 멱등성.
- **`sheet_links`** — 테넌트별 시트 미러링 설정.
  - `id`, `client_id`, `spreadsheet_id`, `tab_name`, `auth_mode`, `last_synced_seq`, `status`.

> Redis는 영속 데이터가 아니라 (a) 멱등성 키 저장소, (b) BullMQ 잡 큐 백엔드로 쓴다. 원천 데이터는 항상 PostgreSQL.

## 8. 주요 API 스펙 (초안)

| 메서드 | 경로 | 설명 |
|--------|------|------|
| `POST` | `/v1/access-events` | 단일 출입 이벤트 수집(멱등). |
| `POST` | `/v1/access-events:batch` | 배치 수집(음영 복구). 이벤트별 결과 배열 반환. |
| `GET` | `/v1/access-events` | 기간·게이트·주체 필터 조회(감사). |
| `GET` | `/v1/occupancy` | 현재 내부 인원 집계(게이트/구역별). |
| `POST` | `/v1/devices` | 단말/기기 + FCM 토큰 등록·갱신. |
| `GET` | `/v1/notifications` | 인앱 인박스 동기화(미읽음 포함). |
| `POST` | `/v1/notifications/{id}:read` | 알림 읽음 처리. |
| `PUT` | `/v1/integrations/sheet` | 테넌트 시트 미러링 설정. |

**공통 규약**
- 인증: `Authorization: Bearer chk_...`.
- 멱등성: 이벤트별 `eventId`가 기준. 배치는 `Idempotency-Key` 헤더 선택 지원.
- 배치 응답 예: `{ results: [{ eventId, status: "accepted"|"duplicate"|"rejected", reason? }] }`.

## 9. 비기능 요구사항

- **성능:** 단일 수집 p95 ≤ 150ms(동기 경로는 DB 커밋까지만). 배치 200건 p95 ≤ 1s.
- **가용성:** 수집 경로 99.9%. 시트/알림은 비동기·재시도이므로 일시 장애가 수집을 막지 않는다.
- **데이터 내구성:** 정상 운영 가정에서 확정 이벤트 유실 0건. 단말 큐 + 서버 멱등 + DB UNIQUE의 3중 방어.
- **보안:** API Key 해시 대조, 테넌트 격리, 전송 구간 TLS, FCM 토큰·시트 자격증명 암호화 저장. 최소 권한 서비스 계정.
- **관측성:** 큐 적체 깊이, 멱등 충돌율, 시트 미러 지연, FCM 실패율을 메트릭으로 노출. 임계 초과 시 운영 알림.
- **확장성:** 수집 API와 워커(시트/알림)를 수평 확장. 멱등성·잡 큐는 Redis가 공유 상태.

## 10. 성공 지표 (KPI)

- **신뢰 지표:** 이벤트 유실률 = 0 유지. 멱등 중복 흡수율(재전송 중 DB 미반영 비율) 100%.
- **속도 지표:** 시트 미러 p95 지연 ≤ 5s. 우선순위 알림 전달(푸시 or 인박스) ≤ 5s.
- **운영 지표:** 음영 복구 후 동기화 완료 시간, 큐 최대 적체 깊이.
- **채택 지표:** 미러링 시트를 주 1회 이상 여는 테넌트 비율, FCM 토큰 활성 기기 수.
